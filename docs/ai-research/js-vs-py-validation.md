## Honest Findings

**Pipeline parity (what this validates):**
- Same NDJSON schema, row count, dim set, cellId set, seed set, scenario set.
- Both implementations preserve the RC3 B1 fix (non-zero DTE rows in all cells).
- Both Bayesian posteriors are internally consistent (Beta prior + observed
  counts → mean ∈ [0, 1], CI width sensible).

**Trajectory divergence (what this does NOT validate):**
- Absolute `bayesianMean` differs by up to 0.5 on 6 dims because of a
  documented semantic null-handling difference:
  - **JS fallback**: optimistic — missing/heuristic `raw` ⇒ `normalized = 1.0`
    ⇒ Bayesian posterior pulls to ~0.75.
  - **Python fallback**: conservative — `raw = null` ⇒ `normalized = 0.0` ⇒
    Bayesian posterior pulls to ~0.25.
- Both implementations are individually consistent; the gap is the 2 × prior
  distance, exactly the symmetric outcome you would expect when one side
  encodes "no answer = success" and the other encodes "no answer = failure".
- Cell-level rank correlation is structurally zero because **both** runs emit
  one constant `bayesianMean` per dim (no cell × seed × scenario differentiation
  is possible without a live LLM).

**Why we did not pursue rank correlation ≥ 0.95:**
The runs use different RNG backends (mulberry32 vs PCG64) and the Python port
has shed ~60% of LOC, so trajectories diverge by design. Cross-implementation
trajectory-level agreement is not a goal of this audit — pipeline parity is.

**With a real LLM in the loop:**
Both implementations should produce non-degenerate cell-level differentiation,
at which point the meaningful target is cell-rank-order agreement between JS
and Python (not value-level agreement). This is left for a future audit pass
once the proxy is wired in production mode for both runtimes.
